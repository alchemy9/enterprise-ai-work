## 01 背景与产品目标

### 1.1 业务背景

项目经理需要从任务台账、项目文档、会议纪要及跨部门反馈中收集信息，整理进度、识别风险，再推动负责人处理。当前痛点集中在资料分散、统计口径不一致、汇总耗时、风险依据难追溯以及整改事项缺少连续跟踪。

平台要解决的是“可信汇总并推进处理”。单纯聊天无法保证业务数字正确，也无法保证任务真实流转；单纯固定表单又无法有效处理纪要、原因和建议等非结构化信息。因此采用“可信业务数据 + 可引用知识 + 受约束分析 + 确定性流转”的组合。

### 1.2 已确认的业务基线

| 项目 | 基线 |
| --- | --- |
| 主项目 | Enterprise AI Work，企业级 AI Agent 智能工作平台 |
| 核心闭环 | Agent 提供分析建议 → 项目经理确认 → 平台创建整改任务并选择负责人 → Workflow 跟踪处理与验收 |
| 效率结果 | 客户验收中，项目进度汇总由原人工约半天缩短至约 5 分钟；5 分钟包含人工审核确认 |
| 结果来源 | 交付阶段客户验收测试，交付一个月后的客户回访支持该改善 |
| 执行边界 | 关键业务决策由人确认；部分业务沟通仍可在线下或微信进行 |

上述结果用于说明业务价值。新增功能的质量、性能和推广效果使用本 PRD 的独立验收口径，不能由既有单一结果推算。

### 1.3 产品目标

G1：员工能够基于授权企业资料获得带出处的回答。G2：项目经理能够生成可核对、可编辑、可审核的进度报告。G3：风险建议可经确认转为可追责的整改任务。G4：企业能够管理权限、版本、运行、质量和成本。

首期成功标准：选定项目与周期后，形成“数据快照 → 规则统计 → 证据检索 → 风险建议 → 人工审核 → 发布归档 → 整改验收”的完整闭环，发生故障时可定位、可恢复且不重复写入。

### 1.4 产品原则

业务数字优先取自可信结构化数据并由规则计算；模型负责理解、归纳与建议。所有敏感读取和写入均由服务端授权。报告发布和整改创建需要明确的人类动作。资料、模型输出、审核修改和正式结果分版本保存。无依据、缺数据和工具失败均须向用户展示，不能伪装为成功。

### 1.5 非目标

R1 不替代企业现有 ERP、OA 或完整项目管理系统，不自动批准付款、签合同、发外部消息或关闭业务任务；不做任意代码执行、通用浏览器代理、多 Agent 自由协商或完整低代码流程设计器；不把 AIPM 的个人产品研究和 PRD 编写主线并入本平台。

## 02 目标用户与业务场景

### 2.1 用户角色

| 角色 | 主要诉求 | 高频动作 | 核心价值 |
| --- | --- | --- | --- |
| 项目经理 | 快速掌握项目进度并推动整改 | 选周期、生成报告、审查、创建整改、验收 | 缩短汇总与协调周期 |
| 项目成员/任务负责人 | 找资料、反馈进展、完成整改 | 问答、更新任务、上传处理证据 | 减少重复解释与遗漏 |
| 部门负责人/PMO | 了解项目状态和重大风险 | 阅读已发布报告、查看授权项目风险 | 统一口径与管理依据 |
| 知识管理员 | 保证资料可用、版本有效 | 上传、解析重试、更新、下架、授权 | 提升知识质量 |
| AI 运营人员 | 保证模板效果稳定可控 | 维护模板、评测、版本发布、监控 | 降低质量波动 |
| 企业管理员 | 管理组织、接入与资源 | 成员授权、连接配置、配额、审计 | 可治理与可追责 |

### 2.2 核心场景与用户故事

| 场景 | 用户故事 | 输入 | 输出 | 优先级 |
| --- | --- | --- | --- | --- |
| S1 知识问答 | 作为项目成员，我希望查到当前项目验收要求并看到原文 | 问题、项目、授权知识库 | 带引用回答或依据不足说明 | P0 |
| S2 进度汇总 | 作为项目经理，我希望快速汇总本周进展并核对来源 | 项目、周期、台账与文档 | 报告草稿、统计表、风险清单 | P0 |
| S3 整改闭环 | 作为项目经理，我希望将确认的问题分配给负责人并验收 | 风险项、负责人、截止日、验收标准 | 整改任务、处理证据、验收记录 | P0 |
| S4 开放分析 | 作为项目经理，我希望分析某项里程碑延误的可能原因 | 自然语言目标、数据范围 | 有边界的执行计划与证据分析 | P1 |
| S5 跨项目管理 | 作为 PMO，我希望比较授权项目的风险趋势 | 项目集合、统一周期 | 组合视图与下钻入口 | P2 |

### 2.3 端到端业务路径

项目经理进入项目空间，检查数据更新时间，选择“项目进度汇总”并填写周期。系统校验权限与数据，冻结一次输入快照，执行规则统计和知识检索，生成带引用报告。审核人检查数字、证据与建议，可编辑、退回或通过。通过后形成正式版本；项目经理对需要执行的建议逐条勾选，补齐负责人、截止日期与验收标准，再创建整改。负责人处理并提交证据，项目经理验收或退回；所有步骤保留时间、操作者和版本。

## 03 版本范围与优先级

### 3.1 优先级定义

P0：缺失会阻断 R1 核心闭环或造成权限、数据、写入风险，R1 发布前必须完成。P1：提升效率、配置和治理能力，安排在 R1.1。P2：需要新场景或收益证据，纳入 R2 储备。P0/P1 是交付顺序，不代表历史完成状态。

### 3.2 版本计划

| 版本 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| R1 核心闭环 | 组织项目权限、文档与 CSV 导入、引用问答、固定汇总模板、人工审核、整改流转、版本与审计、基本运行质量面板 | 关键闭环及权限/并发/故障用例通过；达到第 16 章建议门槛 |
| R1.1 效率增强 | 一个经选定的只读企业数据连接、定时汇总、开放分析 Agent、受控模板配置、知识问答多轮、站内提醒增强 | 连接增量/撤权/故障验证通过，Agent 质量与成本可量化 |
| R2 平台扩展 | 可视化编排、更多连接器、跨项目看板、按需多 Agent、模型策略路由、企业身份深度集成 | 有明确用户需求，收益覆盖新增成本与复杂度 |

R1 使用内置任务台账或经校验的 CSV 快照完成数据闭环，不以企业外部接口接通为前提。第三方读写连接单独评审；内置整改任务创建属于 R1。

## 04 产品架构与模块职责

配套图：Enterprise_AI_Work_产品架构图.png；可编辑源图：Enterprise_AI_Work_产品架构图.svg。

### 4.1 架构分层

| 层级 | 组成 | 职责与上下层关系 |
| --- | --- | --- |
| 用户角色 | 员工、项目经理、知识管理员、运营与企业管理员 | 按角色进入业务工作区或管理区 |
| 产品入口 | 工作台、项目空间、知识问答、管理控制台 | 提供任务发起、资料访问、审核与配置入口 |
| 业务应用 | 知识中心、进度报告、整改协同、成果与待办 | 面向用户交付具体业务成果 |
| 执行与智能 | 模板/Workflow、受约束 Agent、人工确认、任务运行中心 | 控制任务顺序、分析边界、暂停恢复及写入 |
| 共用能力 | 数据与规则、RAG 证据、工具连接、模型服务 | 为执行层提供可信数据、引用、工具与生成能力 |
| 数据资源 | 企业文档、业务台账、业务状态与成果、索引/快照/日志 | 保存原始数据、执行状态和结果证据 |
| 横向治理 | 身份权限、工具授权、质量评测、成本配额、版本审计 | 覆盖所有读取、生成、展示和写入路径 |

### 4.2 四类能力的职责边界

RAG 提供证据，返回可定位的文档片段和版本；规则引擎计算逾期天数、完成率与里程碑状态；Agent 在证据范围内归纳原因、分析风险、生成建议；Workflow 负责校验、顺序与分支、审核等待、执行恢复和结果归档。业务 API 负责最终权限校验、字段合法性、状态转换和幂等写入。

这是一张产品逻辑架构图，模块代表职责划分，可按团队规模合并实现，不要求每个模块独立部署。数据库、模型厂商与编排引擎在技术设计评审决定。

## 05 信息架构与页面要求

### 5.1 导航结构

业务区主导航：工作台、项目空间、知识中心、任务运行、成果中心、审核与待办。管理区主导航：成员与权限、模板与 Agent、工具连接、运行评估、审计与设置。成员只看到获授权的管理入口；导航隐藏之外，所有后端接口仍需鉴权。

### 5.2 关键页面规格

| 页面 | 核心信息与控件 | 状态与交互规则 |
| --- | --- | --- |
| P01 工作台 | 快捷问答、生成汇总、待审报告、我的整改、最近成果、项目筛选 | 无项目时引导申请/创建；不汇总无权项目数字 |
| P02 项目空间 | 项目概况、成员、台账、资料、报告、整改、数据更新时间 | 切换项目清空旧项目临时检索上下文；未保存内容先提示 |
| P03 知识中心 | 库列表、文件、格式、大小、版本、解析/索引状态、有效期 | 区分上传完成与可检索；失败支持查看原因和重试 |
| P04 可信问答 | 输入区、项目/知识范围、回答、引用卡片、反馈 | 证据不足显示缺口；引用打开定位片段，不泄露无权文件名 |
| P05 新建汇总 | 模板、项目、周期、知识库、台账快照、审核人、数据检查 | 必填缺失禁止启动；缺少里程碑等局部数据可确认后降级 |
| P06 运行详情 | 当前节点、起止时间、摘要、已用预算、失败原因、取消/重试 | 不显示虚假百分比；页面关闭后服务端继续执行 |
| P07 报告审核 | 正文与统计、来源侧栏、版本对比、编辑、通过/退回 | 操作基于明确 report_version；过期页面先刷新再操作 |
| P08 整改列表/详情 | 状态、负责人、截止日、来源风险、验收标准、证据、活动记录 | 非法转换不显示入口且服务端拒绝；已验收需新建关联任务继续跟进 |
| P09 成果中心 | 报告/问答收藏、项目、作者、状态、版本、下载记录 | 默认展示本人/项目权限内成果；导出带审核状态和来源 |
| P10 管理控制台 | 成员角色、连接状态、模板版本、评测结果、成本、审计 | 配置保存与发布分开；高权限配置操作留痕 |

### 5.3 共用交互

列表支持按项目、状态、时间与负责人筛选，R1 默认每页 20 条。日期与时间统一展示企业时区，服务端存储时间戳。所有异步操作在提交后返回任务 ID，刷新可恢复状态。错误提示由“发生了什么、影响范围、可采取的动作”组成，并提供排障编号，不能向普通成员展示密钥、原始堆栈或内部提示词。

用户输入、文档标题和模型正文均作为不可信内容渲染；Markdown 禁止执行脚本和危险链接。运行摘要展示步骤、工具和证据，避免把模型内部推理当作可审计的业务依据。

## 06 身份、项目与权限需求

### 6.1 ORG-01 企业与成员（P0）

输入：企业标识、成员账号、显示名、角色、启用状态。管理员可添加/停用成员并授予角色；登录会话必须绑定唯一当前企业上下文。停用后阻断新会话和新操作，撤销既有访问令牌或在下一次受保护请求中判定无效；其历史操作保留操作者标识。

异常：账号重复提示已存在；最后一位有效企业管理员不得被直接停用；成员退出项目后，其拥有的待办需移交或标为待分配，不能静默丢弃。验收：停用成员无法调用历史 URL、下载与任务接口；历史审核记录仍可查询。

### 6.2 ORG-02 项目空间（P0）

项目字段：项目 ID、名称、编号、说明、项目经理、成员、开始/计划结束日期、时区、状态。项目编号在企业内唯一；名称 1～100 字，说明最多 2000 字。状态为进行中、已归档；归档后允许有权读取，禁止发起新汇总、修改台账和创建整改，重新开启须项目经理或授权管理员操作。

创建项目自动建立默认资料区和任务台账。已有未完成整改时，归档需列出清单并由项目经理确认，整改按“继续处理”或“逐条取消并填写原因”的策略处理，R1 默认继续处理；归档不自动关闭整改。验收：跨项目链接校验成员关系，归档项目规则在 UI/API 一致。

### 6.3 ORG-03 项目成员与审核配置（P0）

项目经理管理项目成员并指定有审核权的审核人。审核人必须为有效项目成员，默认项目经理本人；R1 允许生成报告者同时审核，但必须留下明确审核动作和身份记录；需要双人复核的企业列入配置评审。变更审核人需记录前后值、原因和操作人，待审核报告收到新待办。

### 6.4 SEC-01 权限判定（P0）

有效权限 = 有效账号 + 当前租户 + 角色操作权限 + 项目成员范围 + 知识库/对象授权 + 对象当前状态。任何一项失败均拒绝。租户和授权范围由服务端从登录上下文取得，不能直接信任请求参数或模型输出。

| 动作 | 成员 | 项目经理 | 知识管理员 | AI 运营 | 企业管理员 |
| --- | --- | --- | --- | --- | --- |
| 问答、查看已发布报告 | 授权范围 | 授权范围 | 授权范围 | 授权范围 | 授权范围 |
| 发起汇总、审阅草稿 | 被明确授权 | 本项目 | 无默认权 | 无默认权 | 无默认权 |
| 审核发布、创建整改 | 无默认权 | 本项目 | 无 | 无 | 仅被授业务权时 |
| 更新整改处理证据 | 本人负责 | 本项目 | 兼任负责人时 | 兼任负责人时 | 兼任负责人时 |
| 管理文档与知识授权 | 允许上传时 | 本项目 | 被管理知识库 | 无 | 管理授权策略 |
| 发布模板和评测 | 无 | 无默认权 | 无 | 企业范围 | 管理授权策略 |
| 管理成员与系统配置 | 无 | 项目成员 | 无 | 无 | 企业范围 |

系统管理权不自动赋予所有业务文档阅读权。授权管理、内容访问和审计访问分别判定；临时提权必须有期限、原因和审计。

### 6.5 SEC-02 撤权与结果隔离（P0）

撤权应同时作用于检索、引用预览、问答历史、报告、快照、缓存、下载和运行详情。R1 对报告采用保守继承策略：可见范围不得超过项目授权与所有输入资料权限的交集；新增读者若无法覆盖资料范围，不提供完整报告，由有权人员生成脱敏版本另行审核。

来源文件删除或撤权后，不仅禁用链接；对依赖该来源的已保存输出标记受限，重新计算访问范围，不能继续展示其摘要泄露原文。撤权后目标为 60 秒内阻断在线访问；下载到用户设备的副本无法远程撤回，在导出前提示并记录下载人。验收覆盖文档正文、文件名、片段、缓存和历史答案。

## 07 数据接入与知识库需求

### 7.1 DATA-01 结构化任务台账（P0）

支持页面维护和 CSV 导入。CSV 首行字段映射：task_id、title、owner_id、status、planned_start、due_date、completed_at、milestone_id、updated_at。必填 task_id/title/status；进行中任务缺截止日可以导入但计入数据缺失，不纳入可判定逾期样本。负责人必须匹配有效项目成员，不由模型猜测。

导入先预览校验结果：总行数、有效行、错误行、更新/新增数量。R1 每批最多 1 万行；格式错误、未知状态、非法日期、重复 task_id、完成时间早于开始时间均给出行级原因。默认整批原子提交，有错误时修正后重提；用户可下载错误清单，不静默丢行。重复导入按 project_id + task_id 更新并保存批次，不重复创建。

CSV 是当前状态快照，不承诺还原历史。查询过去周期时，若缺少该周期末快照，不能把当前状态冒充历史状态；系统提示“缺少期末快照”，允许改为当前状态报告或补充有效快照。验收包含重复导入、错误回滚和历史缺快照三类。

### 7.2 DATA-02 企业连接与同步（P1）

R1.1 选一个经确认的业务数据源做只读连接。配置项：连接名称、服务地址、授权凭据引用、项目映射、字段映射、同步频率、可读范围。保存前执行连通性与权限测试；凭据仅在密钥服务中保存引用，不下发给模型或前端。记录最近成功同步时间、同步水位、读取条数和失败原因。

增量失败不覆盖最近有效快照；标明数据滞后。凭据到期/撤销后停止读取并通知管理员；连接重新授权后从上次有效水位续传并去重。第三方写入与外发不随只读连接自动开放，需要单独需求与审批策略。

### 7.3 KB-01 知识库与文件管理（P0）

知识库字段：名称、说明、所属项目/企业、负责人、可访问角色与成员、默认有效期。R1 支持 PDF、DOCX、TXT、Markdown 的文本内容，每文件最大 50 MB、每批最多 20 个；容量为建议默认配置。扫描 PDF、加密文件和复杂图表无法解析时明确提示，OCR 与图表理解属于 P1，不将空文本索引为成功。

文件包含 doc_id、版本号、原文件名、业务分类、来源、上传者、更新时间、生效/失效时间、解析状态、索引状态、内容哈希和访问策略。相同库内相同哈希提示重复，可取消或明确作为新版本保存；恶意/不支持文件拒绝接入。验收：上传成功后展示“处理中”，仅索引成功才可检索。

### 7.4 KB-02 解析、分块与索引（P0）

状态链：UPLOADED → PARSING → INDEXING → AVAILABLE；解析/索引失败进入 FAILED 并记录所在阶段。每次处理绑定 doc_version 与 index_version，重试沿用同一处理批次语义，不能生成重复可见分块。

保留标题层级、页码或段落锚点、表格行列上下文。采用子块召回、父段补充上下文的设计，子块与父段同时携带权限、文档版本和定位信息；补充父段时不得越过授权边界。建议初始子块 300～500 tokens、相邻重叠 50～80 tokens，父段 1000～1500 tokens，均为待评测的配置起点，最终由中文资料评测确定。

对表格保留表头并标明单位；数字跨页或合并单元格无法确定含义时标为低质量，禁止作为唯一计算依据。验收：指定测试文档能定位到真实页/段；失败文件可重试且不污染线上索引。

### 7.5 KB-03 更新、失效与删除（P0）

新版本先建立独立索引，校验成功后原子切换 active_version，避免检索混用新旧内容；切换失败保留原可用版本并告警。知识库默认只查当前有效版本；历史核对必须明确选择历史模式并提示。

下架/删除先立即停用检索与访问，再异步清理原文件、索引和缓存；保留内容不可逆清除前的审计元数据。历史报告保留来源版本标识，若内容因删除策略不可访问，仅显示“来源已不可用”，并依 SEC-02 限制含源内容的历史输出。普通软删除保留期建议 30 天；敏感数据立即删除及备份擦除周期需另定策略。

### 7.6 KB-04 检索配置与质量反馈（P0）

检索必须先限定企业、项目、有效期和 ACL 范围。R1 支持语义检索，可结合关键词并重排；候选数和重排阈值由评测集选择。召回分数是检索信号，不直接显示为事实置信度。每个证据对象包含 evidence_id、doc_id/version、chunk_id、标题、页/段、更新时间和受控预览入口。

对用户“未找到/引用不对/资料过期”反馈记录问题、授权上下文、检索版本与 evidence_id；反馈仅向有资料权限的维护者开放。验收：无权资料不得进入检索上下文或日志正文，权限失效立即影响重新查询。

## 08 可信知识问答需求

### 8.1 QA-01 提问与回答（P0）

用户选择项目与知识范围后提问，输入 1～4000 字。R1 单轮问答可独立验收；历史会话用于查看，暂不默认把多轮历史自动注入。P1 多轮需要问题澄清与范围提示，切换项目时重新建立授权上下文。

回答区分“资料事实、归纳解释、行动建议、缺失信息”。有事实性结论时附引用，涉及业务数字则展示数据快照与计算口径。没有相关证据时输出依据不足，并建议补充哪类资料；不得把通用知识包装成企业制度或承诺。用户可以停止生成，已输出部分标为未完成。

### 8.2 QA-02 来源追溯（P0）

点击引用卡片打开侧栏，展示文件名、版本、更新时间、页码/段落和命中片段；打开原文再次鉴权。模型只能引用本次输入的 evidence_id，服务端校验引用存在且归属于本次检索。无效引用返回修复，不渲染虚假编号。两个版本冲突时并列说明版本与生效时间；无法判断当前适用版本则要求知识管理员确认。

### 8.3 QA-03 问答反馈与降级（P0）

反馈选项：有帮助、答案错误、引用错误、信息过期、其他，后四项允许补充说明。检索服务不可用时显示“暂时无法检索企业资料”，可保留问题稍后重试；不自动切成无依据的企业答案。超出个人权限的询问统一提示无可用授权资料，不暴露确有某份机密文件存在。

验收：同一问题在有证据、无证据、冲突证据、无权限和检索失败五种情况下出现不同且正确的结果。

## 09 项目进度汇总需求

### 9.1 RPT-01 任务参数与数据预检（P0）

必填：项目、报告模板、统计开始/结束日期、数据截点、审核人。可选：知识库范围、重点关注项、是否与上期比较。日期按企业时区，开始日 00:00 至结束日次日 00:00 前；结束日期不能晚于今天。若结束日为今天，明确报告截至当前采集时间，不暗示全天数据完整。

启动前展示台账快照时间、条目数、资料数量、最近同步状态、缺失字段与权限范围。无任何任务数据时阻断“进度汇总”，可切换资料摘要模板；部分字段缺失时列出影响指标并由发起人确认后继续。建议数据超过 24 小时未更新显示滞后提示，不自动认为最新。

执行时冻结 source_snapshot_id、文档有效版本清单、模板版本和规则版本；运行中来源更新不自动改写本次输入。启动按钮返回 run_id；相同 submission_key 的网络重发返回原 run_id，用户有意“再生成”使用新 key。

### 9.2 RPT-02 统计规则（P0）

统计对象为数据截点 T 时已存在、未删除且非取消的任务集合 S。R1 完成状态由业务枚举完成值判定，不能由 LLM 从标题推断。以下口径在报告“数据说明”中可展开查看。

| 指标 | 定义 | 缺失/边界处理 |
| --- | --- | --- |
| 任务完成率 | S 中截至 T 已完成任务数 ÷ S 总数 | S 为空显示“不适用”，不显示 0% |
| 本期完成数 | completed_at 落在统计区间且不晚于 T 的有效任务数 | 状态为完成但无完成时间，计入总完成数，不计入本期，另列缺失 |
| 未完成逾期 | 截至 T 未完成且 due_date 早于 T 对应本地日期 | 当天到期不算逾期；无截止日列为不可判定 |
| 逾期天数 | T 的本地日期减 due_date，按自然日计算 | 不按模型估算，不混用工作日 |
| 完成时逾期 | 已完成且完成本地日期晚于 due_date | 与“当前未完成逾期”分开展示 |
| 里程碑状态 | 里程碑计划日、完成状态与其绑定任务共同形成规则结果 | 缺里程碑数据则本节标缺失，不生成虚构里程碑 |
| 上期变化 | 当前和上期期末快照在相同指标定义下求差 | 缺任一期快照则不比较，不从当前状态倒推 |

多任务的平均进度仅在存在已确认权重规则时计算，R1 不默认用简单平均替代整体项目进度。示例：S 共 10 项、已完成 4 项，则任务完成率 40%；另有未完成且截止日在 T 前的 2 项，未完成逾期为 2，不受“风险描述”文字影响。

### 9.3 RPT-03 报告生成与结构（P0）

正式结构：①报告概况与数据截点；②关键统计与口径；③本期完成与主要进展；④进行中、逾期与里程碑；⑤风险与问题；⑥建议整改清单；⑦下周期关注事项；⑧数据缺口与引用清单。

风险字段：risk_id、标题、事实描述、相关任务、等级、规则触发项、证据 IDs、可能原因、影响说明、建议动作、待确认项。逾期天数、任务状态和业务值从规则结果填充；原因属于分析性推断，需标注“可能”，不能把相关性当事实。负责人和截止日仅作建议时清晰标注，创建整改前必须由用户确定。

风险等级建议由可配置规则提供初值：关键里程碑逾期或阻塞关键交付为高；普通任务逾期且存在下游依赖为中；资料不完整或一般跟进为低。关键里程碑/依赖字段缺失时不按该规则升级；模型可提议调整等级，但需给出依据，人工最终确认。此分级需在业务评审中固化。

### 9.4 RPT-04 结果校验与重新生成（P0）

校验包括必填章节、数字与快照一致、引用属于本次证据、风险字段完整、不得包含无权内容。失败先进行一次限定修复；仍失败进入需人工处理状态，禁止直接进入可发布。重新生成创建独立 run_id 与报告草稿版本，保留旧版及差异，不覆盖审核中的版本。用户已编辑内容只能在明确确认后用于新版本，不能被后台自动覆盖。

验收：修改源台账后旧报告数字不变；新生成报告引用新的快照。审核页面能查看“AI 原稿/人工修改/正式版”差异。

## 10 Agent、Workflow 与任务运行

### 10.1 AG-01 受约束 Agent（P0 基础分析；P1 开放规划）

R1 的 Agent 是固定流程中的分析节点，只读取当前步骤允许的业务字段和证据，并输出风险/建议 Schema。P1 开放分析入口允许用户输入目标，Agent 生成可见计划：任务目标、查询步骤、所需工具、数据范围、预计预算、预期成果。计划中不得移除人工审核或扩大权限。

只读分析在既有权限内可执行；任何写入或外发需产生待确认动作卡片。工具默认白名单，建议上限为每任务 8 次工具调用、3 次规划循环、300 秒运行预算，均作为 R1.1 待压测默认值。达到预算停止并保留部分结果，不无限循环；预算不包含等待人工审核的时间。

文档中的“忽略规则、调用其他工具、泄露密钥”等文字只作为资料内容，不能成为指令。允许工具由服务端判定；工具参数做 Schema 校验；模型不接触真实密钥。验收：恶意资料不能让模型越权读取、调用未授权工具或绕过审核。

### 10.2 WF-01 内置工作流（P0）

进度汇总内置流程：参数与权限校验 → 读取快照 → 规则统计 → 检索证据 → Agent 分析 → 输出校验 → 保存草稿 → 等待人工审核。审核通过后进入发布归档；创建整改由用户另一次明确提交触发，避免“报告通过”被当作执行全部建议的授权。

R1 配置只允许修改模板参数、提示词、工具范围和规则阈值，面向运营人员；不提供任意拖拽生产节点。每次执行绑定不可变的 workflow_version、prompt_version、model_config_version、rules_version、retrieval_version。旧任务继续使用原版本，新发布配置仅影响新任务。

### 10.3 RUN-01 运行状态与过程展示（P0）

| 状态 | 用户含义 | 允许动作 | 后续状态 |
| --- | --- | --- | --- |
| QUEUED | 已受理，等待执行 | 取消 | RUNNING / CANCELLED |
| RUNNING | 节点正在执行 | 请求取消 | WAITING_REVIEW / FAILED / CANCELLING |
| WAITING_REVIEW | 草稿已保存，等待审核 | 查看、审核、撤回 | REVIEW_REJECTED / COMPLETED / CANCELLED |
| REVIEW_REJECTED | 已退回，等待修改 | 编辑草稿并重提审核；重新生成 | 重提后 WAITING_REVIEW；重新生成另建运行 |
| FAILED | 已失败，保留失败点 | 查看、受控恢复 | 恢复使用新 attempt，返回 RUNNING |
| CANCELLING | 正在阻止后续步骤 | 查看 | CANCELLED / FAILED |
| CANCELLED | 已终止，无新执行 | 复制参数新建 | 终态 |
| COMPLETED | 已审核并完成发布归档 | 查看、导出 | 终态 |

每节点记录 started_at、ended_at、attempt、输入/输出摘要、引用、错误码和执行版本。只向有权人员显示脱敏摘要；普通用户看到业务步骤，运营人员按权限下钻调用日志。任务的生成耗时、排队时间、人工等待时间分别统计。

### 10.4 RUN-02 失败重试与人工接管（P0）

临时网络、限流与 5xx 可最多自动重试 2 次，建议退避为 2 秒、5 秒并添加抖动，超过预算停止。401/403、参数错误和资料缺失不盲目重试；引导修复权限或补数据。模型 Schema 不合格最多修复 1 次。人工接管允许下载当前草稿、补录修订并按正常审核流提交，不可直接改数据库或跳过审核。

恢复从服务端保存的节点和输入版本开始。修改项目、周期、数据范围后必须新建任务；不能复用旧执行状态。遇到结果不明的写操作，先用原幂等键查结果，再决定重试。验收：Worker 重启、页面关闭和消息重复投递都不会造成重复整改。

### 10.5 RUN-03 取消与恢复边界（P0）

取消在持久化后阻断尚未开始的节点和副作用。等待审核时取消，须同步作废当前审核单并将未发布报告退回草稿，旧审核入口不可继续通过。进行中的只读工具可等待超时返回，但返回结果不得继续触发新步骤。已经成功提交的业务写入不能因取消被自动撤销；界面明确列出“已创建任务”及其后续处理入口。取消与创建并发时，由服务端操作锁/状态比较决定写入是否获准，记录最终结果，不能只依赖前端停止按钮。

### 10.6 RUN-04 工具调用策略（P0）

| 工具类型 | 示例 | 执行规则 |
| --- | --- | --- |
| 授权读取 | 查台账、检索资料 | 校验租户/项目/对象；受调用数与时间限制 |
| 生成计算 | 规则统计、生成报告草稿 | 不改变业务状态；保存数据和版本来源 |
| 业务写入 | 创建内置整改任务、发布报告 | 用户明确提交，校验最新权限、参数、版本与幂等 |
| 外发/高风险 | 外部消息、付款、关闭外部业务任务 | R1 关闭，不因接入连接而自动开放 |

MCP 或 HTTP/API 仅是后续连接实现方式，不改变授权要求。凭据、平台规则和工具名单均不由模型输出决定。

## 11 人工审核与整改闭环

### 11.1 APR-01 报告编辑与提交审核（P0）

报告状态：DRAFT → IN_REVIEW → APPROVED → PUBLISHED；退回 IN_REVIEW → CHANGES_REQUESTED → DRAFT；撤回 IN_REVIEW → DRAFT；旧正式版由新正式版发布后标记 SUPERSEDED，仍可按权限查看。

编辑生成新 report_version，保留 AI 原稿；提交审核时冻结版本及其 hash，并建立 approval_id、审核人和提交时间。审核中版本只读，若要改内容须先撤回；不能让审核人通过一个已被替换的正文。数值修改要求填写原因并标记为人工调整，不悄悄冒充数据源结果。人工新增事实可补充文件或业务引用，缺引用时显示人工补充标签。

### 11.2 APR-02 审核决策与并发（P0）

审核操作：通过、退回；退回必填原因，通过可选备注。点击通过显示将发布的版本、目标读者范围和数据截点。服务端重新校验审核权限、对象版本、内容 hash、源访问策略和审核单状态。重复提交相同决策返回既有结果；过期页面返回版本冲突并刷新，不覆盖别人操作。

R1 为单人审核。待审提醒建议 24 小时，7 天后提示长期未处理，可由项目经理撤回或转交；不自动通过。转交只变更审核人并保留记录。审核人离职、停用或移出项目，任务进入待转交队列。拒绝不是运行故障，不自动重试模型。

### 11.3 APR-03 发布与变更（P0）

审核通过后提交发布；R1 可在“通过并发布”一次明确点击完成，但内部仍保存两条独立事件。发布只面向平台内已授权成员，不发送外部消息。写入失败时保留 APPROVED，显示“发布失败待重试”，用同一版本和幂等键恢复，不能要求重新批准未变更的内容。

正式版正文只读；修订必须派生新草稿并重新审核。旧版保留发布者、时间、版本和替代关系。发布前来源撤权或关键数据策略变动时暂停，要求重新检查；不会因旧审批自动放行。

### 11.4 FIX-01 从风险创建整改（P0）

报告审核和整改创建是两个业务动作。项目经理在已发布报告勾选风险，逐条填写/确认：标题 1～100 字、问题描述、负责人、截止日期、验收标准、来源 risk_id、来源 report_id/version、优先级。缺负责人、截止日或验收标准不得创建；负责人必须是有效项目成员，日期不得早于当天。

确认页展示实际将创建的任务清单和字段；提交按单条风险生成稳定 action_id。幂等键建议 tenant_id + report_id + report_version + risk_id + action_type；同一风险同一报告版本默认只创建一条整改。需要拆分时由用户显式增加 action_id 并填写拆分说明。批量提交逐条返回成功/失败，重试只处理失败条目，已成功项保留任务链接。

### 11.5 FIX-02 处理、反馈与状态（P0）

| 状态 | 允许动作与操作者 | 规则 |
| --- | --- | --- |
| TODO 待处理 | 负责人开始；项目经理改派/取消 | 改派记录原负责人、原因与时间 |
| IN_PROGRESS 处理中 | 负责人更新处理记录并提交验收 | 必填处理说明，证据附件按验收标准要求 |
| PENDING_ACCEPTANCE 待验收 | 项目经理通过/退回 | 负责人不能自行验收；退回须说明 |
| REWORK 退回整改 | 负责人继续处理并重提 | 保留上次提交与退回记录 |
| ACCEPTED 已验收 | 有权人员查看 | 终态；再次发生问题创建关联新任务 |
| CANCELLED 已取消 | 项目经理取消未验收任务 | 原因必填，已验收不能取消 |

状态 TODO/IN_PROGRESS/REWORK 超过截止日显示逾期；PENDING_ACCEPTANCE 显示待验收超时，避免把审核等待全部算作负责人处理延误。负责人只能修改处理内容，不能改验收结论与审计。项目经理调整截止日需填写原因并保存调整前后的值。

### 11.6 FIX-03 验收与追溯（P0）

通过验收记录验收人、时间、验收结果与说明；不满足标准退回 REWORK。页面可从整改跳转到来源风险、报告版本、原始证据；引用按当前权限控制。线下沟通可由负责人/项目经理补录“沟通摘要”，但不得自动把聊天描述当作已经完成或验收。

验收：一条风险完整经过确认创建、分派、处理、提交、退回、再提交、验收；每个状态变动均可追踪，且重复提交不生成新任务或重复记录。

## 12 成果、历史、导出与提醒

### 12.1 OUT-01 成果与历史（P0）

报告、运行、审核、整改通过稳定 ID 关联。成果中心按项目、类型、状态、时间和作者筛选；复制任务只复用参数，不复用已授权结论、过期凭据或旧审批。历史结果显示数据截点、资料版本、审核状态和当前访问限制。收藏仅保存引用关系，不扩大对象权限。

### 12.2 OUT-02 导出（P0）

R1 支持 Markdown、DOCX；PDF 作为 P1。导出包含标题、项目、周期、数据截点、审核状态、版本、导出人/时间、指标口径和来源清单。草稿可由有草稿权人员导出，醒目标记“未经审核”；导出正式版不得混入未审核修订。导出引用为受控链接或明确来源标识，不生成永久公开资料 URL。

导出开始和下载时均鉴权，下载地址短期有效，建议 10 分钟；后台生成失败保留任务并可重试。记录下载审计，不在导出正文泄露隐藏字段、其他租户数据、内部提示词或密钥。

### 12.3 MSG-01 待办与通知（P0）

R1 站内通知覆盖：报告待审/退回/发布、整改分配/改派/退回/待验收、解析失败、运行失败。每条通知绑定 business_event_id 去重，有已读/未读状态和对象入口；对象已撤权时只提示事项不可访问，不能通过通知标题泄密。

提醒失败不回滚已完成业务写入，记录失败并重投；通知重投不能再次创建业务对象。P1 增加可配置站内催办与订阅；邮件/飞书/企业微信外发先单独配置接收人范围、授权和内容脱敏，再评审。

## 13 运营、配置与治理

### 13.1 OPS-01 模板与 Agent 版本（P0）

模板包含名称、场景、输入 Schema、输出 Schema、提示词、知识范围规则、工具白名单、预算、审核要求和版本。状态为 DRAFT、TESTING、PUBLISHED、DISABLED；已发布版本不可原地编辑。运营人员复制新版本、跑评测、填写变更说明后发布，必要时回滚到已验证版本。

模板禁用后不接受新任务，正在运行任务按原版本继续或由管理员明确取消。权限策略升级、工具撤销等安全变更即时生效，不因“绑定旧版本”继续放行。R1 提供基础配置表单和发布记录，完整画布为 R2。

### 13.2 OPS-02 运行质量与成本（P0）

面板按企业、项目、模板版本、日期展示：任务数、成功/失败、审核等待、端到端耗时、生成耗时、工具错误、tokens、单任务成本与预算命中数。业务失败、系统失败和用户取消分别统计；没有账单单价时显示用量与待配置，不捏造金额。

达到企业配额前告警，达到硬限额阻断新模型任务，保留查询历史和人工整改操作。运行中预算用尽停止后续模型调用并保存部分结果。模型切换仅可使用经授权且完成同级数据策略评审的配置，并重新验证质量，不能静默把敏感资料发往其他供应商。

### 13.3 OPS-03 审计与追踪（P0）

审计对象：登录/停用/授权、文档访问与删除、检索、任务发起/取消/恢复、模型与工具调用元数据、审核、发布、整改、导出、配置变更。每条包含 tenant_id、actor_id、action、object_id、timestamp、request_id/trace_id、结果和变更前后摘要。

审计按独立权限查询且不可由业务普通成员改删。日志默认脱敏，不记录原始密钥、完整身份凭据或所有文档全文；排障需要内容样本时做专门授权和保留期控制。R1 支持按项目、对象、人员和时间检索并导出授权范围的审计记录。

### 14.3 任务 State 最小结构

run_id / tenant_id / actor_id / project_id / period / cutoff_time / source_snapshot_id / document_versions / template_versions / task_metrics / retrieved_evidence[] / risk_items[] / report_id_version / approval_id / allowed_tools / budget_used / node_status / error / trace_id。

各节点只能更新允许字段，权限信息来自平台，不能由 Agent 覆写。输入快照、规则结果和证据对象分区保存；只向当前模型节点提供必要字段，避免把所有日志和资料无限堆入上下文。

### 14.4 一致性与幂等

幂等键在服务端有唯一约束，原始请求摘要相同才返回旧结果；相同键对应不同字段返回冲突。审批/状态转换使用对象 version 做乐观锁。业务对象与事件在同一事务提交，通知/索引用可靠事件异步处理；外部服务返回不明时通过原幂等键查询核对。目标为同一逻辑动作只生效一次，不宣称跨服务天然“恰好一次”。

本章数值为建议验收基线，需按试点数据规模和部署条件签署，不是现有生产性能承诺。

| 编号 | 要求 | 建议验收口径 |
| --- | --- | --- |
| NFR-01 交互 | 常规列表/详情/状态查询 | 100 在线用户、20 并发查询时 P95 ≤ 2 秒；不含模型生成 |
| NFR-02 异步受理 | 新建汇总/导出返回任务 ID | P95 ≤ 3 秒；长任务不占用同步请求直到完成 |

| NFR-04 汇总 | 单项目≤2000 任务、≤50 份相关文本文件 | 5 并发汇总时机器处理 P95 ≤ 180 秒；排队与人工时间独立记录 |

| NFR-08 撤权 | 在线路径访问阻断 | 权限变更后 60 秒内，检索/历史/引用/下载均拒绝无权访问 |
| NFR-09 保留 | 日志、运行、正式成果 | 审计建议 180 天；运行摘要 90 天；正式成果按企业项目档案策略，评审确定 |
| NFR-10 兼容 | PC Web | Chrome/Edge 当前及前一主版本，Safari 当前版本；1366×768 可完成主流程 |

## 16 指标体系、效果评估与发布门槛

### 16.1 指标定义

| 指标 | 定义/分母 | 用途 |
| --- | --- | --- |
| 全流程完成耗时 | 从资料可用并开始汇总，到报告人工确认完成的墙钟时间，包含审核 | 与原人工流程比较，不能只计模型时间 |
| 机器处理耗时 | RUNNING 至草稿保存，排除排队和人工等待，单列重试时间 | 评估系统性能 |
| 报告可用率 | 完成审核且无需重大事实纠正的报告数 ÷ 完成审核报告数 | 评估业务质量 |
| 端到端任务成功率 | 完成发布的有效任务数 ÷ 所有有效发起任务数；另列取消与待审 | 评估完整闭环，避免仅统计成功调用 |
| 引用有效率 | 可打开且确能支持相应结论的引用数 ÷ 被审核引用数 | 验证出处及支持关系 |
| 检索命中率 | gold 依据至少命中一次的问题数 ÷ 有标准依据问题数 | 评估召回与切块 |
| 人工接管率 | 转人工补救的运行数 ÷ 有效运行数 | 识别流程失败成本 |
| 整改按时验收率 | 截止日前验收通过数 ÷ 本期到期且非取消整改数 | 评估后续闭环，需明确等待验收责任 |
| 单次有效成果成本 | 对应周期模型/工具可归集成本 ÷ 已审核有效成果数 | 避免以低价无效调用掩盖浪费 |

### 16.2 业务效率复测

对“约半天 → 约 5 分钟”建立可重复测量方案：同一批项目和周期、等价输入、相同报告质量标准，对比人工流程与平台流程；统一起止事件并记录资料准备、生成、人工修改与审核时间。建议至少 20 组配对任务，报告中位数、P90、样本范围、失败及人工补救，不把历史结果强制设为每次任务 SLA。

### 16.3 评测集与判分

建议首期 100 个经授权脱敏用例：40 个有答案问答、15 个无答案/版本冲突、15 个权限与注入攻击、15 个汇总规则与数据缺失、15 个审批/整改/故障场景。每个保存输入、期望依据、正确统计、允许动作、评分规则、资料版本和责任人；用例只能由有对应资料权限的人员访问。

问答判分包含事实正确、证据支持、缺失处理和权限；报告判分包含数字一致、风险依据、结构完整和可执行性。事实/权限由规则与人工复核为主，模型评分只作为辅助。至少两名评审复核关键争议，保留结论；训练/调试样本与最终留出验收样本分开。

### 16.4 建议发布门槛

| 门槛 | 目标 |
| --- | --- |
| 权限与敏感写入 | 验收集中越权泄露、未确认写入为 0；任一失败阻断发布 |
| 结构化数字 | 汇总规则固定集正确率 100%，缺数据按规定标示 |
| 引用 | 有效且支持结论的引用比例 ≥95%；虚构引用 0 |
| 问答 | 有答案问题事实正确率 ≥90%；无答案/冲突问题正确处理率 ≥95% |
| 核心流程 | 所有 P0 用例通过；故障恢复/幂等/审核并发用例通过率 100% |
| 运行稳定性 | 试点有效样本的机器任务完成率 ≥95%，同时公开失败分布 |
| 性能 | 按第 15 章负载口径完成测试；超标项经评审调整范围后重新验证 |

任何阈值都应写明样本量与数据版本。改模型、提示词、检索、工具或规则，先跑对应回归集，权限与写入用例始终必跑。

## 18 研发交付、依赖与发布

### 18.1 交付工作包

| D 审核与整改 | 编辑版本、审批、发布、整改、站内待办 | C；状态与权限契约 | 端到端闭环及幂等用例通过 |

不按未经评估的日期承诺开发周期。评审后由研发结合人员、复用程度、模型服务和数据连接条件给出排期；P0 边界必须整体闭环，不能只交生成页面。

### 18.2 上线前材料

业务方提供脱敏样本、字段映射、有效知识版本与审核责任人；研发提供接口契约、状态持久化、权限设计和回滚方案；测试提供固定用例、故障注入和隔离结果；运营提供模板版本、评测报告、配额与告警配置；产品提供页面原型、规则解释、用户操作说明及试点复测表。

### 18.3 试点与回滚

先在单一项目和小范围成员开放，观察完整的生成、人工审核和整改周期，再扩大项目范围。发布前备份配置并记录数据迁移版本；模型/模板质量回退可切回已验证版本，权限策略与新增写入记录不得回滚丢失。系统故障时保留历史读取和人工业务入口，暂停新模型任务。恢复后核对运行状态、业务结果与幂等记录，再补偿失败事件。

### 19.2 主要风险及应对

资料质量差：解析质量提示、样本评测、失败重试；历史数据缺失：明确快照能力边界，不生成虚假趋势；错误风险建议：证据与人工审核；权限泄漏：检索前过滤、结果继承与访问重验；流程重复执行：幂等键、状态版本、事务事件与对账；模型成本或延迟上升：预算、配额、限次调用与暂停新任务；用户不愿更新台账：降低导入成本并呈现数据更新时间，不能用 AI 掩盖数据陈旧。

## 20 附录

### 20.1 进度报告字段示例

报告标题：P1 项目周进度报告；周期：2026-11-02 至 2026-11-08；数据截点：2026-11-08 23:59（企业时区）；快照：SNAP-EXAMPLE-001；任务总数：10；已完成：4；完成率：40%；当前未完成逾期：2。以上为统计规则演示数据，不是项目业绩。

风险示例：R-001“验收环境联调滞后”；事实：任务 T-008 未完成、计划截止 11 月 6 日；规则：截至 11 月 8 日逾期 2 个自然日；证据：台账快照记录与会议纪要片段 E-003；可能原因：接口联调条件未齐备，需项目经理确认；建议：明确联调条件与责任人。系统不把“可能原因”直接写成定论，不自动创建整改。

整改确认示例：标题“补齐验收环境联调条件”；负责人由项目经理选择；截止日期由项目经理确认；验收标准“环境连通性检查完成并上传结果”。点击确认后创建 action_id，保存来源报告版本与风险项。

### 20.2 术语

RAG：检索授权资料并将证据提供给生成环节。Agent：在目标与工具边界内执行智能分析或有限规划。Workflow：可持久化、可校验、可恢复的流程执行。Snapshot：某一时间的数据快照。Evidence：带版本、定位和权限的引用依据。ACL：对象访问授权。幂等：同一逻辑请求重发不重复产生业务结果。Trace：跨节点关联的运行记录。
